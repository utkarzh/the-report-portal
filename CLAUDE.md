# Editorial Research Tool — CLAUDE.md

## What we're building

A web platform for **The Report Company** (Phase 01) that lets their editorial team generate AI-powered research and interview questions using Claude. Replaces individual Claude.ai subscriptions with one shared API account.

**End-to-end flow:**
1. Admin invites a user by email → sets their role and monthly token limit
2. User clicks the invite link → signs up → lands on their role-specific dashboard
3. User picks a research category, fills in subject details, clicks Generate → Claude produces the research
4. Admins manage users, prompts, categories, and monitor usage/costs

**Two roles:**
- `admin` — full access: manage users, prompts, categories, view all analytics
- `user` — freelancers/limited staff: generate research up to their monthly token limit

## Architecture Patterns

### Middleware (the access-control layer)
`src/middleware.ts` runs on every non-API, non-static request:
- Unauthenticated → redirects to `/login`
- Deactivated user → signs them out → redirects to `/login?error=account_deactivated`
- Non-admin hitting `/admin/*` → redirects to `/dashboard`
- Injects verified profile into request headers (`x-user-id`, `x-user-role`, `x-user-name`, `x-user-tokens-used`, `x-user-token-limit`)
- The `auth.getSession()` call and the per-navigation `profiles` lookup are both timeout/cache-guarded — see **Middleware auth resilience & the profile cache** below.

### Header-based profile reads (zero extra DB calls)
Server components under `/admin` call `requireAdminHeader()` and `getProfileFromHeaders()` — reads middleware-injected headers, no DB round-trip.

### API routes authenticate themselves
API routes are excluded from the middleware matcher. Each API route calls `getApiUser()` (see below, NOT a bare `supabase.auth.getUser()`) and checks the role via `supabaseAdmin` (service role). Never trust client-sent headers in API routes.

### Middleware auth resilience & the profile cache
Two related fixes, both born from the same underlying fact: auth-js puts no timeout on its calls to Supabase Auth, and a plain Postgres round-trip from middleware runs ~100-400ms depending on network path — either one, unguarded, makes navigation feel randomly slow or hung.
- `middleware.ts`'s `getSession()` races an 8s timeout; a stall on a protected route redirects to `/login?error=service_unavailable` instead of hanging the whole navigation (public routes just render through).
- The per-navigation `profiles` lookup (role/status/permissions/token counts, injected into headers) is cached in a short-TTL (20s), HMAC-signed cookie — [profile-cache.ts](src/lib/auth/profile-cache.ts) — so most navigations skip the DB round-trip entirely. Signed so a client can't forge or extend it (tampering just forces a live re-check); scoped to the exact `user_id` so it can't survive a user switch on a shared browser. Gated behind `MIDDLEWARE_CACHE_SECRET` — unset (the default) means every navigation does the live check exactly as before. **Deliberate tradeoff, explicitly approved for this app (not a banking tool):** while the cache is enabled, deactivation and one-device-login kick-out can take up to the TTL to actually take effect instead of being instant. If that tradeoff is ever reconsidered, don't "fix" it by just deleting the cache — talk to whoever owns that call first.

### Supabase clients — three variants
- `createSupabaseServerClient()` — server components and API routes, uses anon key + cookies
- `createBrowserClient()` — client components
- `supabaseAdmin` — service role, used only in API routes for privileged ops (invite, delete user, etc.)

## Database Schema (key relationships)

```
auth.users (Supabase managed)
  └── profiles (1:1, CASCADE on delete)
        ├── invitations.invited_by  (SET NULL on delete)
        ├── invitations.accepted_by (SET NULL on delete)
        ├── research_sessions.user_id (nullable, SET NULL on delete — keeps history)
        ├── categories.created_by   (SET NULL on delete)
        ├── general_prompt.updated_by (SET NULL on delete)
        ├── general_prompt_versions.saved_by (SET NULL on delete)
        └── category_prompt_versions.saved_by (SET NULL on delete)

research_sessions
  └── messages (CASCADE on delete)

categories
  └── category_prompt_versions (CASCADE on delete)
```

**Important:** `research_sessions.user_id` is nullable on purpose. When a user is deleted their research history is kept (US-011 requirement). Analytics must null-check `user_id` and group deleted-user sessions under "Deleted user".

### Login flow (two paths)
- **Admins** sign in with email + password.
- **Normal users** enter their email and click Sign In. The server mints a one-time
  code and emails it directly to that user's own address. They enter the code to
  finish signing in.

  Single smart form (`/login`): email → `/api/auth/login-init` detects the role and
  returns `password` (admin) or `otp` (user). The OTP is a Supabase code from
  `admin.generateLink({type:'magiclink'})`, emailed via `src/lib/email/smtp.ts`, and
  verified client-side with `verifyOtp`.

### One-device-one-login (all roles)
Every account may be signed in on only one device at a time; the newest login wins.
- On any successful sign-in, the client calls `/api/auth/session-register`, which
  writes a fresh `active_session_id` to the user's `profiles` row and mirrors it into
  an httpOnly `device_session` cookie.
- Middleware compares the cookie against `profiles.active_session_id` on every request.
  A mismatch (the account was signed in elsewhere) clears the cookies and redirects to
  `/login?error=signed_in_elsewhere`.
- Enforcement is skipped while `active_session_id` is NULL, so sessions predating this
  feature stay valid until their next sign-in.

### Transcription module
- **Two providers, chosen by `NEXT_PUBLIC_TRANSCRIPTION_PROVIDER`:**
  - **`assemblyai` (default, does speaker diarization):** compress the whole file in-browser to a compact 16kHz mono MP3 (`transcodeToMp3`, [src/lib/ffmpeg-client.ts](src/lib/ffmpeg-client.ts)) → upload just that small MP3 → submit ONE async transcript job with `speaker_labels: true` ([src/lib/assemblyai/client.ts](src/lib/assemblyai/client.ts)) → client polls to completion → speaker-labelled raw transcript (`Speaker A: …`). Compressing before upload keeps big source files (e.g. a 157 MB WAV → ~11 MB MP3) off Supabase Storage — cheaper and under the storage file-size limit — and the one MP3 serves both the job and in-app playback. No chunking/splitting: diarization needs the whole recording so speaker identities stay consistent. AssemblyAI fetches the audio from a short-lived Supabase signed URL, so it never hits our request body. Job id is stored in `transcribe_job_id` (migration 007) for polling/resume. Route: [transcribe-assemblyai/route.ts](src/app/api/transcriptions/[id]/transcribe-assemblyai/route.ts) — POST submits, GET polls.
  - **`openai` (legacy, no diarization):** the chunked/streaming path described below. Kept as a fallback until AssemblyAI is fully proven, then removable.
- **Translate flow (optional, independent of refine):** the raw transcript can be translated into ONE of `English | German | Spanish | Italian | Russian | Japanese` ([TRANSLATION_LANGUAGES](src/lib/transcriptions.ts)). `POST /api/transcriptions/[id]/translate` streams Claude (`claude-sonnet-4-6`; see cost note below) with a fixed translation system prompt that preserves speaker labels, and stores the result in the single translation slot (`translated_transcript` + `translation_language`, migration 009) — re-translating overwrites it. Token-gated and billed exactly like refine. Raw, translated, and refined are three independent branches off the raw transcript; all are saved and each has its own `.docx` download (`?variant=raw|refined|translated`). Both translate and refine now ACCUMULATE onto the transcript's `tokens_*`/`cost_usd` totals (and each increments the user's global budget). **Japanese has no PDF export** — the PDF pipeline's embedded font ([fonts.ts](src/lib/download-templates/fonts.ts)) is a Latin+Cyrillic-only subset, so CJK glyphs would silently render broken rather than error; `TRANSLATION_LANGUAGES_WITHOUT_PDF` disables the PDF option in the download picker and the download route 422s if hit directly. Word is unaffected (fonts are referenced by name, not embedded, so Word substitutes glyphs itself). Adding another CJK/RTL/Indic language to `TRANSLATION_LANGUAGES` needs the same addition to `TRANSLATION_LANGUAGES_WITHOUT_PDF` unless the font subset is regenerated to cover it.
- **Refine flow (works for both providers):** saved refining prompt (singleton `transcript_prompt`) + the chosen source transcript → Claude (`claude-sonnet-4-6`, streamed) → refined transcript. `POST /refine` takes `{ source: 'raw' | 'translated' }` (defaults to `raw`); the UI refines the raw transcript directly, but when a translation also exists it first pops a picker asking which one to clean up. The result overwrites the single `refined_transcript` slot regardless of source. With AssemblyAI the raw transcript carries real `Speaker A:` / `Speaker B:` labels, so the default refining prompt (migration 008) instructs Claude to PRESERVE those labels verbatim rather than strip or guess them. (Migrations 005/006 wrote the old no-diarization prompts; 008 upgrades any DB that still has either default and 001 ships the new text for fresh installs.)
- **OpenAI flow:** upload audio → **in-browser transcode + split** (ffmpeg.wasm) → per-chunk streaming transcription (OpenAI `gpt-4o-transcribe`, SSE) → raw transcript → optional AI refine (Claude, using the admin-managed **refining prompt**, streamed) → refined transcript. Original audio, chunk audio, raw transcript, and refined transcript are all persisted (`transcriptions` row + private storage bucket).
- **Why chunking (serverless):** the app runs on serverless (Vercel), which has a hard request-time limit, and OpenAI caps transcription at 25 MB / ~25 min per request. So the browser uses **ffmpeg.wasm** ([src/lib/ffmpeg-client.ts](src/lib/ffmpeg-client.ts)) to downsample to 16kHz mono MP3 and split into 10-min chunks. Each chunk is transcribed in its **own short serverless request**, orchestrated sequentially by the client ([TranscriptionWorkspace](src/components/transcriptions/TranscriptionWorkspace.tsx)). This removes both the size and the timeout ceilings, so hour-long recordings work. ffmpeg core is self-hosted under `/public/ffmpeg` (copied on `postinstall` by [scripts/copy-ffmpeg-core.mjs](scripts/copy-ffmpeg-core.mjs); gitignored).
- **Upload path:** the browser uploads the original file (for playback) **and** each chunk *directly* to the private `transcription-audio` bucket (RLS-scoped to the user's own `<uid>/` folder), then `POST /api/transcriptions` records the row with `chunk_paths[]`. Keeps large audio off the API request body. `transcribe/route.ts` transcribes one `chunkIndex` per call and joins per-chunk text into `raw_transcript` when the last chunk lands (resumable — the workspace restarts from the first pending chunk).
- **Interviewee metadata is required at upload** (migration 024: `full_name`/`title_position`/`company_org`/`publication` on `transcriptions`) — [TranscriptionUploader.tsx](src/components/transcriptions/TranscriptionUploader.tsx) blocks the transcribe button until all four are filled in. These exist solely to feed the standardised document header on export — see **Formatted document standard** below — not used anywhere in the transcription/refine pipeline itself.
- **The uploaded audio is downloadable via `GET /api/transcriptions/[id]/audio`** (302 to a fresh 60s signed URL with a download filename) — same pattern as the Sales Coach audio route. Gated by an email allowlist, `TRANSCRIPTION_AUDIO_ADMIN_EMAILS` in [transcription-admins.ts](src/lib/transcription-admins.ts) — deliberately the same three people as `SALES_COACH_ADMIN_EMAILS` ([sales-coach-admins.ts](src/lib/sales-coach-admins.ts)), but kept as its own list (sibling-builder pattern) since this one is only about audio download, not a broader Transcription admin role. The link renders under the audio player in [TranscriptionWorkspace](src/components/transcriptions/TranscriptionWorkspace.tsx) via a `canDownloadAudio` prop computed server-side in the `[id]` page from the caller's email.
- **Refining prompt** mirrors the interview general prompt exactly: singleton `transcript_prompt` + `transcript_prompt_versions`, versioned with snapshot-on-save and rollback, managed at `/admin/transcript-prompt` via `/api/transcript-prompt`. The shared `PromptVersionHistory` component handles all three prompt types (`general` | `category` | `transcript`).
- **Cost/limits:** the Claude refine step counts against the user's token limit (gated pre-flight like research). OpenAI transcription is billed separately and is not counted in token usage. **Model choice:** every user-facing workflow — research, question generation, refine, translate, business cases, editorial briefs — runs on `claude-sonnet-4-6` (`$3/$15` per 1M in/out). Refine and translate briefly ran on `claude-haiku-4-5` to cut cost (they rewrite the whole transcript, so output dominates), but were **deliberately moved back to Sonnet for output quality** in commit `67cab80` — don't "optimise" them back to Haiku without re-checking transcript quality first. The only Haiku call left is the sub-cent input-screening gate (see **Input screening** below). Per-model pricing lives in [tokens.ts](src/lib/claude/tokens.ts) (`SONNET_PRICING` / `HAIKU_PRICING`); `calculateCost(usage, pricing)` takes the profile so the ledger records the real cost — pass the pricing that matches the model you called. Refine and translate each also append a `usage_events` ledger row (see **Usage ledger & analytics** below), so their Claude spend shows in analytics; AssemblyAI transcription is free and untracked.

### Usage ledger & analytics
- **`usage_events` is the append-only source of truth for cost analytics** (migration 010, satisfies US-016a). Every Claude call appends ONE immutable row via `logUsageEvent()` ([src/lib/claude/usage.ts](src/lib/claude/usage.ts)) with a `workflow` of `research` | `research_web_search` (the Gemini searching behind an Interview Tool research run) | `research_questions` | `transcript_refine` | `transcript_translate` | `business_case` | `editorial_brief` | `input_validation`, plus tokens, cost, web_searches, model, `source_id` (no FK — survives item deletion), and `status`/`error`. `usage_events.workflow` is plain TEXT with no CHECK constraint, so adding a workflow needs no migration — but DO add it to `UsageWorkflow` in [types/index.ts](src/types/index.ts) and to both `WORKFLOW_LABELS` and `WORKFLOW_ORDER` in the analytics page, or it won't render.
- **Analytics reads `cost_usd` from the ledger, never re-derives it.** Every headline, per-workflow, and per-user figure is a sum of the per-row `cost_usd` written at call time with that call's own model pricing, so a mixed-model ledger totals correctly. The one exception is the display-only input/output/search split ([analytics/page.tsx](src/app/(admin)/admin/analytics/page.tsx)), which prices output at the Sonnet rate and derives input as the residual — the total is always exact, only the split can skew, and only for non-Sonnet rows.
- **Capturing usage from a stream:** a streamed call's token counts come from the **final** message. Routes that read `claudeStream.finalMessage().usage` get them exactly. The document route can't — it may abort mid-stream at the soft deadline — so it accumulates from stream events, and `output_tokens` arrives **only** on `message_delta`, at the end. A pass cut short therefore sees no output count at all; it recovers one via `messages.countTokens()` on the text it received. **If you add another abortable streaming route, do the same** — otherwise cut-short passes silently bill as if the model wrote nothing, which is most of the real cost.
- **Why a ledger:** usage used to be stamped onto the mutable `research_sessions`/`transcriptions` rows. Regenerating research OVERWROTE those totals (analytics lost every regeneration) and transcription spend was never in analytics at all. The per-item rows still carry their own totals for the item UI (`cost_usd` accumulates there), but `/admin/analytics` reads the ledger — so it counts every regeneration and includes transcription cost. The user's global budget (`profiles.tokens_used`) is charged cumulatively and independently, exactly as before.
- **Analytics** ([src/app/(admin)/admin/analytics/page.tsx](src/app/(admin)/admin/analytics/page.tsx)) supports date ranges (this month / last month / last 30 days / all time via `?range=`), a cost-over-time trend, a per-workflow breakdown, and a per-user table — all from the ledger. Charts are deliberately monochrome to match the app's design language.

### Document modules (Business Cases, Editorial Briefs)
Both run ONE generic engine keyed by `doc_type`; everything that differs lives in [documents.ts](src/lib/documents.ts) (`DOC_TYPES`) — labels, slug, permission flag, `maxTokens`, `maxWebSearches`, `tokenReserve`, `lengthGuidance`. Add a third document type there, not by forking the route.

- **Prompt assembly** ([generate/route.ts](src/app/api/documents/[id]/generate/route.ts)): system = `SEARCH_POLICY` (dated, recency rules) + the admin prompt snapshot + `OUTPUT_CONTRACT`. The contract is placed **last on purpose** so it overrides the admin prompt — several admin prompts describe a Claude.ai-style "write it in chat, then build a Word doc" flow, which makes the model narrate. Note `lengthGuidance` in the task block can contradict the page count in the DB prompt; the code wins.
- **Segmented generation:** one document is written across several passes. A pass ends when it hits the route's soft deadline OR Claude's own `max_tokens` — neither means the document is finished. Only the `<<<DOCUMENT_COMPLETE>>>` marker (or the model ending its turn) means done. The client **auto-continues**: [DocumentOutput](src/components/documents/DocumentOutput.tsx)'s `runToCompletion()` chains passes until done, capped at `AUTO_CONTINUE_MAX` rounds, with a Stop control; reaching the cap or stopping falls back to the manual Continue button. Reopening a mid-run session does NOT auto-resume — the user decides when to spend more.
- **The soft deadline must be a timer, not an in-loop check.** The loop only advances when a stream event arrives, and the SDK's iterator yields no keepalive (`RawMessageStreamEvent` has no `ping`), so during a quiet stretch — a server-side web-search round-trip — an in-loop deadline cannot fire and the function sails past the platform's hard cap, skipping the persist/billing/logging that follows the loop. It's a `setTimeout` that calls `claudeStream.abort()`, with the loop wrapped so only our own abort is swallowed.
- **Vercel duration:** with fluid compute (default on new projects) Hobby is **300s default and maximum** — the older 60s Hobby cap no longer applies. `maxDuration = 300` with a 15s margin gives a 285s soft deadline; override via `DOC_GEN_SOFT_DEADLINE_MS` only if the real cap differs. An early version chunked at a fixed `ROUND_MAX_TOKENS = 2500` to fit the assumed 60s window; that's gone — passes now use the type's full `maxTokens`, so a brief needs ~2-4 rounds, not a dozen.
- **Incremental persistence:** the route saves `output` every ~2.5s while streaming, so even a hard kill loses at most a couple of seconds, and the client's `recoverSaved()` picks up the saved text on a dropped stream.
- **Input screening** ([validate-inputs.ts](src/lib/claude/validate-inputs.ts)): `POST /api/documents` screens the submission **before** creating the session, so placeholder or off-topic input (a one-letter country, "write me a python script") can't spend a full document's budget. A free local check first, then a `claude-haiku-4-5` JSON verdict. Deliberately **permissive** (approve when unsure) and **fails open** on API error — it's a misuse guard, not a security boundary. Rejections return **422** with a user-facing reason. Only the document modules are gated; the interview/research module is not.

### Commercial Meeting Preparation module
Prepares TRC sales reps for meetings with company CEOs / government officials, per the client-authored brief (`docs/TRC_Commercial_Meeting_Prep_Brief_v1_1.pdf`, translated to user stories in `docs/TRC_Commercial_Meeting_Prep_User_Stories_v1.pdf`, US-021→US-032). Gated by `can_access_meeting_preparation` (profiles/invitations), wired through [access.ts](src/lib/access.ts)/middleware/Sidebar exactly like the other modules — **not** part of the `DOC_TYPES` engine, since its workflow is multi-stage/stateful rather than one-shot.

- **Schema** (migration `014_meeting_preparation.sql`): `meeting_prep_sessions` is the workflow's state machine — `stage` walks `input → researching → awaiting_review → points_generating → points_pending → planteo_generating → planteo_pending → final_generating → complete` (or `failed` at any point). `research_sections` (JSONB: `interviewee`/`organisation`/`motivation_profiles`/`quotes_news`) and `presentation_points` (JSONB string array) hold the two structured, editable-by-piece outputs; `planteo_output`/`final_output` are plain text. Each of the 4 sequential prompts (`meeting_prep_prompt`, keyed by `prompt_key`) and the 2 fixed Planteo Library variants (`meeting_prep_planteo_library`, keyed by `variant`) is versioned (`*_versions` tables) via the shared [PromptVersionHistory](src/components/admin/PromptVersionHistory.tsx) component (`type: 'meeting_prep_prompt' | 'meeting_prep_planteo'`). Publications come from the central **Media Library** (migration 039; `meeting_prep_media_library` is now a compatibility view over it): a publication with no Meeting Prep media profile there (positioning / audience & reach / narrative focus all empty, `hasMeetingPrepProfile()`) is listed but disabled in the form and halts Step 1 with zero API cost (US-022), per [`src/app/api/meeting-prep/route.ts`](src/app/api/meeting-prep/route.ts). Sessions snapshot the profile, so editing it never changes a past session.
- **Four sequential Claude calls, one per stage**, each its own route under `src/app/api/meeting-prep/[id]/` (`research`, `points`, `planteo`, `final-document`), each independently token-gated right before its own call (`MEETING_PREP_*_RESERVE` in [tokens.ts](src/lib/claude/tokens.ts)) and each logging its own `usage_events` workflow (`meeting_prep_research` | `meeting_prep_points` | `meeting_prep_planteo` | `meeting_prep_final_document`). A stage only starts once the prior stage's output is approved — enforced by checking `session.stage` at the top of each route, not just in the UI.
- **Research output uses marker-delimited sections, not JSON.** The research prompt is instructed to emit `<<<SECTION:INTERVIEWEE>>>` etc. as literal markers; [`parseResearchSections`](src/lib/meeting-prep.ts) splits on them. This was chosen over asking the model for a JSON object because the section bodies are long, citation-heavy markdown — safely JSON-escaping that from a streaming model is fragile, while splitting on a unique literal marker isn't. The internal narrative validation step (US-026, invisible to the user) runs as a second Sonnet call with a `json_schema` verdict (mirrors [validate-inputs.ts](src/lib/claude/validate-inputs.ts)'s pattern) and is capped at **one** reframe retry so a stubborn miss can't loop cost indefinitely.
- **Per-section regeneration is new plumbing, not reused from elsewhere.** Every other AI-output surface in this app (research, business cases, editorial briefs) streams one flat text blob where "regenerate" means discard-and-restream the whole thing — there was a `messages`/chat table for finer-grained refinement once, but it was deliberately dropped (see `supabase/teardown.sql`). `POST /api/meeting-prep/[id]/research/regenerate` takes `{section, feedback}`, sends only that section's slice of context (plus the other three accepted sections, shown but marked "do not contradict") back to Claude, and overwrites just that one JSONB key — every other section and any user edits already saved are untouched. The presentation points ("regenerate one of three" / "reframe all three") use the same targeted-vs-full pattern; the planteo, being one continuous spoken script, only supports full regeneration with feedback.
- **Direct manual edits** (no AI call) for research sections, presentation points, and the planteo go through a single `PATCH /api/meeting-prep/[id]` with an allowlist of editable fields, rather than a route per field.
- **Final document QC** (US-031): the closing instructions inside the `final_document` prompt assert the brief's full checklist (every claim sourced, no overt motivation labels, correct planteo variant, ≤4 pages, etc.) — that's the real check. [`final-document/route.ts`](src/app/api/meeting-prep/[id]/final-document/route.ts) adds one cheap heuristic backstop on top: a regex check that all six fixed section headings are present, triggering exactly one corrective re-prompt if any are missing.
- **`.docx` export** reuses the Business Case/Editorial Brief template's markdown→docx renderer (`renderTokens` and the shared style constants, exported from [docx-template.ts](src/lib/docx-template.ts)) but needs its own cover page (interviewee/title/company/publication instead of country/media-partner), so it has a dedicated sibling builder in [meeting-prep-docx.ts](src/lib/meeting-prep-docx.ts) rather than forcing this module into `DocTypeConfig`.
- **Known gap:** Appendix A (the actual approved planteo scripts for both variants) had not been delivered by the TRC commercial team as of this build — the Planteo Library ships with the mechanism fully wired (admin-editable, versioned) but empty `template_text` for both variants until that content is supplied.

### Interview Request Letter & Email Generator module
Turns a small set of project inputs into an approved one-page Interview Request Letter (built paragraph-by-paragraph against an admin-managed universal template), then a **separately drafted** cover email — its own document with its own admin-managed prompt, not a condensed copy of the letter — with optional per-recipient personalization once both are approved — per `docs/TRC_GFDI_Interview_Letter_Email_Generator_User_Stories_v1.pdf` (Module 5, US-049→US-061). Modeled directly on the Commercial Meeting Preparation module above (the spec names it as the closest precedent) — same multi-stage/stateful shape, same marker-delimited AI output, same per-piece regeneration against "do not contradict" context, same versioned-template pattern via `PromptVersionHistory`. Gated by `can_access_interview_letter_generator` (profiles/invitations), wired through [access.ts](src/lib/access.ts)/middleware/Sidebar exactly like the other modules — not part of the `DOC_TYPES` engine, for the same reason meeting-prep isn't.

- **Schema** (migration `021_interview_letter_generator.sql`): `interview_letter_projects` is the workflow's state machine — `stage` walks `input → researching → hook_review → letter_generating → letter_review → letter_approved → email_generating → email_review → complete` (or `failed`, reachable only from the streaming research call — every other AI call in this module is a single awaited non-streaming request that never persists an in-progress stage, so there's nothing else that can get stuck mid-flight; see the `resetStalledStage` note below). `paragraphs` (JSONB, shadowing the live `interview_letter_templates.structure` for the project's company) holds one entry per template slot — fixed slots start pre-`locked` (never model output, never re-approved), variable slots start `pending` until the user approves them. `interview_letter_templates` (keyed by `company IN ('TRC','GFDI')` and, since migration 038, `variant IN ('anchor','no_anchor')`) is versioned (`interview_letter_templates_versions`) via the shared [PromptVersionHistory](src/components/admin/PromptVersionHistory.tsx) component (`type: 'interview_letter_template'`) — since that component's contract is a plain `prompt_text` string, the JSON `structure` is serialized/deserialized at the API boundary (`JSON.stringify`/`JSON.parse`), not inside the component. Both companies are seeded with placeholder 6-slot structures at migration time (the spec's own words: "build and test with placeholder wording now; real copy can be dropped in later without a schema change") — a company with an empty/missing template halts project creation with a 422 and zero API cost, mirroring meeting-prep's media-library halt.
- **The research step's system prompt is admin-editable per company** (migration `022_interview_letter_research_prompt.sql`, `interview_letter_research_prompts` + versions, admin UI at `/admin/interview-letters/research-prompt/[company]`) rather than hardcoded — mirrors `meeting_prep_prompt`'s versioned-singleton pattern exactly, keyed by `company` instead of a fixed stage-key set. Unlike the document module's SEARCH_POLICY + admin-prompt + fixed OUTPUT_CONTRACT split, there is no separate immutable contract appended after the admin prompt here: the `<<<HOOK>>>`/`<<<BULLETS>>>` marker instructions live inside the admin-editable text itself (seeded there by default), matching meeting-prep's research prompt — the existing `repairFormat` reformatting pass is the safety net if an edit ever breaks the markers.
- **The email step has its own admin-editable, versioned, per-company prompt** (migration `023_interview_letter_email_prompt.sql`, `interview_letter_email_prompts` + versions, admin UI at `/admin/interview-letters/email-prompt/[company]`, `PromptVersionHistory` `type: 'interview_letter_email_prompt'`) — same pattern as the research prompt above. This replaced an earlier version where `POST /api/interview-letters/[id]/email` hardcoded an `EMAIL_SYSTEM` string instructing Claude to write "a condensed version of the approved letter"; real TRC/GFDI cover emails are a genuinely different document (own subject-line convention, signed by a different role than the letter, referencing the attached letter, citing prior published report examples, covering interview-scheduling logistics) than the formal letter they accompany. The route builds `system` as `${adminPromptText}\n\n${NO_PREAMBLE_INSTRUCTION}` and passes project context (company/country/media partner) plus the sender block below alongside the approved letter and confirmed hook; `.../email/regenerate` wraps the same admin prompt with a "you are revising, not drafting fresh" instruction layered on top, mirroring how letter regenerate reuses the template's per-slot instructions. Both routes write the fully-assembled system prompt to `email_prompt_snapshot` (what was actually used for that run), and both halt with a 422 (zero API cost) if no email prompt is configured for the company, mirroring the letter-template halt at project creation.
- **Cover-email sender identity is a per-project input, not a template default** (migration `023`, `sender_name`/`sender_title`/`sender_contact` on `interview_letter_projects`, collected on `ProjectSetupForm` alongside company/project country/media partner). The real signer varies by project/reporter — unlike the letter, which keeps one fixed per-company signature — so this is asked once per project and threaded into both the initial email generation and every regenerate call.
- **Letter generation is one Claude call producing every variable paragraph at once**, not N separate calls — `<<<PARAGRAPH:key>>>` markers (same technique as `parseResearchSections`) let [`parseParagraphMarkers`](src/lib/interview-letters.ts) split one response into per-slot text. This is what "generated paragraph-by-paragraph … not one long completion split up afterward" (US-053) actually means: discrete marked units the model is asked for directly, not free prose regex-chopped after the fact — not literally one HTTP round-trip per paragraph.
- **Per-paragraph regeneration** (`POST /api/interview-letters/[id]/letter/regenerate`, US-054) sends only the target slot's instructions/word-budget plus every OTHER *locked* paragraph as "do not contradict" context — direct reuse of meeting-prep's per-section regenerate pattern. A paragraph must be `pending` to regenerate. Once `Approve`d (`POST .../letter/approve`, no AI call) it's `locked`; since 19 Oct 2026 `POST .../letter/unlock` (the paragraph card's "Edit") puts it back to `pending` during `letter_review` (see **Step navigation** below).
- **Final Approve** (`POST .../letter/final-approve`, US-055) is a validation + snapshot step, no AI call: every variable paragraph must be `locked`, plus a heuristic one-page word-count ceiling (`ONE_PAGE_WORD_LIMIT` in [interview-letters.ts](src/lib/interview-letters.ts)) — same spirit as the final-document module's regex heading-check backstop, not real pagination. Passing snapshots the joined paragraph text into `master_letter` and flips `stage` to `letter_approved`.
- **Personalization bundles the letter AND email in one action** (`POST .../personalize`, US-058): a single Claude call returns both via `<<<SECTION:LETTER>>>`/`<<<SECTION:EMAIL>>>` markers, stored as one row in `interview_letter_personalizations` per recipient (unlimited per project, CASCADE-deleted with it). All five recipient fields are optional; senior-official address conventions are applied by prompt instruction, not client-side logic.
- **Non-streaming routes never set a "failed" stage.** Unlike the streaming research call — which persists `stage: 'researching'` before its async work can die mid-request, so it needs the `failed` terminal state plus `PATCH .../route.ts`'s `resetStalledStage` recovery path — every other call here (`letter`, `letter/regenerate`, `email`, `email/regenerate`, `personalize`) is a single awaited `messages.create()`: on error the project's `stage` is simply left untouched (still `hook_review`/`letter_review`/etc.) and the real spend is still billed via `logUsageEvent`, so the client just retries the same button with no separate recovery UI.
- **Download (Word or PDF, in a branded template)** (`GET .../export`, [interview-letter-docx.ts](src/lib/interview-letter-docx.ts) + [interview-letter-pdf.tsx](src/lib/interview-letter-pdf.tsx), both fed by `buildLetterLayout()` in [interview-letter-export.ts](src/lib/interview-letter-export.ts) so they can't drift). It is offered from Final Approve onwards: on the approved-letter screen, on email review, at complete, and per personalized letter. It uses the same `DownloadTemplateModal` picker as Topic Outline/Transcript downloads (header/footer bands from download-templates). **Laid out like the client's real letters (sample: TRC × Foreign Policy, 18 Oct 2026):**
  - a centred bold header "Interview Request" / "Name, Title, Company" / "For publication in <Media>", with the media name not italic, unlike Topic/Transcript;
  - the identity line highlighted yellow while it's still the placeholder;
  - the export month and year right-aligned and highlighted;
  - justified prose, with the publication's name in bold italic;
  - the signature's `Name`/`Position` placeholder lines highlighted, and multi-line blocks set one line per paragraph, left-aligned (justifying a line that ends in a manual break stretches it);
  - any other `[bracket]` gap highlighted, except in the "Dear [Name]," salutation.

  **Filled downloads come out complete (19 Oct 2026, "why are we asking things twice?"):**
  - The dialog asks only for the recipient (name / designation / company-ministry). The name also fills "Dear [Name],"; personalized letters already carry the AI's salutation.

It only acts on lines before the salutation, and only on a short line *starting* "For publication in", because the shared `stripLeadingPublicationHeader()` would also match prose like "scheduled for publication in January". Page geometry, font and spacing come from the shared **Formatted document standard** below (Calibri 11pt, 1.15, 1.9 cm / 2.5 cm), not from `docx-template.ts`. The PDF uses Tinos, because Calibri can't be embedded. **File name** `letterDownloadName()`: "Interview Request Letter – Name, Title, Company". It is filled from the personalization's recipient, or for the master letter from the dialog's optional recipient fields (new `fields`/`fieldsHint` props on `DownloadTemplateModal`; function `filenameBase`). With no recipient it falls back to the project country. The route sends an RFC 6266 `filename*` header (`attachmentDisposition()`) so the "–" survives in every browser.

### Knowledge Base module (Module 7, migration 034)
Staff ask how TRC does something and get answers only from approved, published company knowledge, per `TRC_Knowledge_Base_User_Stories_v3.pdf` (US-097→US-123). Gated by `can_access_knowledge_base`, wired through [access.ts](src/lib/access.ts)/middleware/Sidebar like every other module. User/Guardian pages live under `/knowledge` (Ask, Browse, My suggestions, Manage); the admin area lives **inside the module** at `/knowledge/admin` (departments, members, chat log), reached from the gold "Admin tools" strip at the top of the module like every other module's admin tools — it is not in the sidebar's global Admin section. Because it's outside `/admin/*`, the middleware's admin rule doesn't cover it: every page there calls `requireKbAdmin()` ([page-context.ts](src/lib/knowledge/page-context.ts)), which redirects non-admins to `/knowledge`. Old `/admin/knowledge/*` URLs redirect via `next.config.js`. Shared presentational pieces (type tiles, avatars, department monograms, stat tiles, empty states) are in [kb-ui.tsx](src/components/knowledge/kb-ui.tsx) and the module header/tab strip in [KnowledgeHeader.tsx](src/components/knowledge/KnowledgeHeader.tsx).

- **Departments are the permission boundary, enforced in ONE place:** [knowledge/access.ts](src/lib/knowledge/access.ts). A user sees (and the AI searches) only the published knowledge of departments they're a member of or guard; admins see every live department. Membership is read live on every request — never cached — so removal applies on the next request (US-099). Every `knowledge_*` table has RLS enabled with **no policies**: all access goes through API routes/server components using the service role after these checks. Don't add client-side Supabase reads for this module; extend `access.ts` instead.
- **One Guardian per department** (`knowledge_departments.guardian_id`, nullable). Only that Guardian can create, edit, publish or archive the department's knowledge (`requireGuardian()`); admins manage departments/members but are **read-only on content** (the spec: admins don't publish). With no Guardian, or a deactivated one, the department stays live but read-only, and admin pages show a warning (US-122). Feedback/drafts are routed by department, not by person, so changing the Guardian needs no data migration. Assigning a Guardian auto-grants them the module flag.
- **Draft → publish via a pointer.** `knowledge_items.published_version_id` is THE live version; `draft_version_id` is the pending edit. Editing a published item copies it into a draft (`ensureDraft()`); publishing indexes the draft first, then flips the pointer in one guarded UPDATE. `knowledge_search()` only matches chunks whose `version_id` equals the item's `published_version_id` (and `status='published'`, department not archived), so drafts never change answers, the old and new versions are never both live, and archiving takes effect instantly. Old version rows are kept (audit + restore; restore creates a draft, never goes live directly); superseded versions' chunks are deleted.
- **Indexing** ([indexing.ts](src/lib/knowledge/indexing.ts)) runs from the Publish button, resumable in ~240s slices (the client calls `/publish` again while it returns `{done:false}`). Chunks upsert on `(version_id, chunk_index)` and only chunks still missing an embedding are embedded, so retries never duplicate. The chunker ([chunking.ts](src/lib/knowledge/chunking.ts)) never truncates, keeps whole sections together when they fit and labels every piece of a split section with its heading path. Tested on a 1.3M-character document: no text lost, max passage 2,600 chars, deterministic. Any edit to a draft's indexable content resets its partial index (`resetVersionIndex`).
- **Hybrid search, embeddings optional.** `knowledge_search()` fuses Postgres full-text (`tsv`, always available) with pgvector cosine similarity (`text-embedding-3-small` via OpenAI, only when `OPENAI_API_KEY` is set), using reciprocal rank fusion. There's no ANN index on purpose (exact scan respects the department filter; add HNSW + iterative scan past ~100k chunks). Semantic hits need ≥0.25 similarity, so an off-topic question returns nothing and the chat route answers "no approved answer" **without a Claude call**.
- **Extraction** ([extract.ts](src/lib/knowledge/extract.ts)): PDF (unpdf, per page), .docx (mammoth HTML → light markdown so Word headings survive for the chunker), .txt/.md. Files upload straight to Storage via server-minted signed upload URLs (`/api/knowledge/upload-url`, Guardian-checked), then the browser calls `/api/knowledge/versions/[id]/extract` per file (2 at a time in bulk upload). Too little readable text (e.g. a scanned PDF) → `needs_attention`, which blocks publishing (US-107; no OCR in Phase 1). A run stuck in `processing` for 6+ min shows a Retry.
- **Chat** (`POST /api/knowledge/chat`, SSE, `claude-sonnet-4-6`): token-gated before any cost (`KNOWLEDGE_BASE_QUERY_RESERVE`); retrieval limited to the caller's live departments; up to 8 items / 60k chars of passages, grouped per item in document order (so two sections of one big document are both citable). The model cites `[S#]` tags and opens with `[[NO_ANSWER]]` when the sources don't answer it (held back server-side so it never flashes). `sources` is stored as a **snapshot** (title, department, Guardian, last updated) so history still renders after an item is archived; `used_version_ids` records every version handed to the model. Answers asking for examples also pull items marked `is_example`. On failure the question (and an empty new chat) is deleted — no partial save — and the client offers Retry.
- **Feedback & suggestions** share `knowledge_feedback` (`kind`). "Helpful" is stored as `done` and never queued; other ratings go to the department of the first cited source (or the user's department; the modal asks which if they have several). Guardians act on the queue at `/knowledge/manage/[deptId]?tab=review`: Accept opens the source item as a draft (or a new-guide form for "new knowledge"), Decline takes an optional note shown to the user under My suggestions.
- **The app keeps working before migration 034 is run** ([schema-compat.ts](src/lib/knowledge/schema-compat.ts)). The middleware's per-navigation profile select names `can_access_knowledge_base`; on a pre-034 database that select fails with `42703`, which the middleware would read as "no profile" and sign everyone out. So the middleware, the users page, the invite route and the user-edit route retry without the column when `isMissingKbColumn()` matches (the module just reads as off), and every Knowledge Base page redirects to `/knowledge/setup` while `knowledgeBaseInstalled()` finds no tables. Keep this in place until 034 has run on every environment. Any future module that adds a column to the middleware select needs the same guard.
- **Ledger:** `knowledge_base_query` (one row per question, incl. no-answer ones at ~zero cost; includes query-embedding cost) and `knowledge_base_indexing` (embedding tokens/cost per publish slice). Embedding tokens are not charged to anyone's token budget.

### Country Intelligence module (migration 037, Oct 2026)
Builds a country intelligence report — a long list of local companies that meet TRC's commercial criteria, each with a profile and a named person to approach — for a sponsored country/sector report (first use: Poland, sectoral security report for the Munich Security Conference, Feb 2027). It productises a run that was first done by hand from the terminal. Pages are under `/commercial/country-intelligence` (list, `/new`, `/[id]` workspace); the system prompt editor is at `/commercial/admin/country-intelligence`. **v1 is admin-only**: gated by role in middleware (`blockedFromCountryIntel`), the section `layout.tsx` (`requireAdminHeader()`), and every API route (`requireCiAdmin()` in [auth.ts](src/lib/country-intel/auth.ts)). There's no `can_access_*` flag yet; adding one means adding a column to the middleware's profile select, which needs the Knowledge Base's schema-compat guard.

- **Runs on Gemini, not Claude** ([gemini.ts](src/lib/country-intel/gemini.ts), REST `streamGenerateContent?alt=sse` with the `google_search` tool, `GEMINI_API_KEY`). Grounded web research at this scale (hundreds of companies) is far cheaper there. The research model is `CI_RESEARCH_MODEL` (default `gemini-3.8-flash`); `CI_DEEP_MODEL` (default `gemini-3.1-pro-preview`) is used only for the Deep tier's company-selection step. Prices are in `priceFor()`. **3.8 Flash doubles on 1 Jan 2027, and `priceFor()` already applies that by date.** Google Search grounding has 5,000 free queries a month, so search cost is booked only when `CI_BILL_SEARCHES=1`.
- **A reply with zero `webSearchQueries` is rejected, never used.** In the manual run, ungrounded replies were confirmed to be fabricated (invented revenues and phone numbers). The client streams the reply and **aborts at the first text chunk if no grounding metadata has arrived**, so a skipped search costs a fraction of a cent rather than a full reply. `ground()` in [engine.ts](src/lib/country-intel/engine.ts) retries up to 4 times and then re-queues the task. Grounded calls use question-style prompts with plain `|`-separated rows or `@@ COMPANY:` labelled-line output ([prompts.ts](src/lib/country-intel/prompts.ts), [parse.ts](src/lib/country-intel/parse.ts)), not JSON. JSON-shaped prompts made the model skip search far more often. Only the ungrounded selection step returns JSON.
- **Resumable task queue, driven by the open page.**
  - `ci_tasks` holds every unit of work, each of kind `context`, `collect`, `select`, `profile`, `contacts` or `verify`.
  - [ResearchWorkspace](src/components/country-intel/ResearchWorkspace.tsx) calls `POST /api/country-intel/[id]/step` in a loop, in the same spirit as the documents module's auto-continue.
  - Each step works for up to ~240s. It claims tasks with `ci_claim_tasks()` (`FOR UPDATE SKIP LOCKED`; a lock older than 7 min is reclaimed) and runs 3 at a time.
  - Each step stops claiming new tasks after 150s, and a call that needs more time than the request has left throws `Defer`, which re-queues the task for free.
  - **Nothing may outlive the request, because Vercel kills it at 300s and skips the saving and billing that follow.** Every Gemini call times out at `min(time left − 12s, 230s)`, so it ends by ~228s. Website checks are bounded too: `execVerify` starts no new company after ~220s, and its fetcher (`makeFetcher(timeout, hardStop)`) stops every fetch at ~275s. A company cut short isn't saved; it's re-queued with the rest via `Defer`.
  - If everything claimed in a batch had to `Defer`, the step ends rather than re-claiming the same tasks in a tight loop. The client waits 4s after a step that returns in under 3s (another tab, or a still-locked task, holds the work).
  - The 300s cap is per request, not per run: a one-hour run is ~15–20 separate step requests.
  - Phase changes (`context_discovery → selecting → profiling → [next round] → contacts → verifying → done`) are compare-and-set on `(phase, round, status)`, so two open tabs can't plan the same phase twice.
  - **The run only advances while someone has the workspace open.** There's no cron, because Vercel Hobby crons run only daily. Closing the tab pauses the run in place, and reopening it continues.
- **Users choose the size and the depth, and that sets the cost.** Users pick the target count (10–300) and Quick, Standard or Deep (`DEPTHS` in [depth.ts](src/lib/country-intel/depth.ts)). Depth sets:
  - discovery questions per sector
  - profile batch size and detail
  - whether there's a contacts pass and a country-context pass
  - the number of discovery rounds
  - the selection model

  `estimateRun()` gives a live estimate on the form, and the editable **hard stop** defaults to 1.6× that estimate. Checked against the Poland run's real figures: Standard, 150 companies, 7 sectors ≈ $2.9 expected (≈ $4.7 hard stop). Quick ≈ $1.7 and Deep ≈ $5.0.
- **The budget is a hard stop, checked before every call.** The check is `spent + worstCaseCost(call) > budget`. All spend goes through `ci_add_spend()`, which is atomic. Reaching the stop pauses the project with an error starting `BUDGET:` and keeps the phase, and resuming requires raising the budget (`PATCH {action:'resume', budgetUsd}`). Every call, including aborted ones, also appends a `usage_events` row (`country_intel_context` | `country_intel_discovery` | `country_intel_profiles` | `country_intel_contacts`).
- **The criteria are applied in code, never taken from the model's label.** `assess()` in [criteria.ts](src/lib/country-intel/criteria.ts) works out the verdict:
  - revenue in USD ≥ the project's `min_revenue_usd` (default $60M) → **Qualified**
  - no confirmed figure, or figures that conflict by more than 2.5×, but real scale indicators → **Likely qualified**
  - anything else → **Outside criteria**
  - a foreign ultimate parent (when `local_hq_only`, the default; this is the "no MNCs unless the HQ is in the country" rule) and companies in liquidation are excluded

  When too few companies pass, the engine runs another discovery round that excludes every name it already has, up to the depth's `maxRounds`. Companies on the client's own list are always profiled. Any that fail the criteria go in a separate "client list — outside criteria" section with the reason, not into the main list.
- **Contacts are business contacts only, and each one is checked.** The `verify` pass ([verify.ts](src/lib/country-intel/verify.ts)) costs nothing (no AI call). It fetches the company's own pages: the site root, press/media/IR paths and subdomains, and the parent page of each cited URL. It checks each phone number, mobile, email and name against them. A detail that's confirmed shows ✓, and one that can't be confirmed shows ⚠ but is **kept, not dropped**. Dropping them lost real numbers in the manual run. Junk filters remove placeholder numbers and generic GDPR mailboxes, and a number that appears for several companies without confirmation is blanked. People are ranked press > marketing > board office > IR. The prompts forbid private contacts and guessed numbers.
- **Exports** (`GET /api/country-intel/[id]/export?format=pdf|xlsx`). Both are built from `buildReportModel()` ([report-data.ts](src/lib/country-intel/report-data.ts)).
  - The PDF ([report-pdf.tsx](src/lib/country-intel/report-pdf.tsx)) follows the client's Italy sample layout:
    - a field table per company, with a blue contact block ("Who to approach", other contacts, switchboard, suggested approach) after the leadership rows
    - a total on every sector heading ("N companies in this sector · T in the whole report")
    - appendices: contact directory, country context, excluded companies
    - the embedded Tinos font, so Polish and other Latin Extended text renders correctly
  - The Excel file ([report-xlsx.ts](src/lib/country-intel/report-xlsx.ts)) has Companies, Contacts (with ✓ columns), the client list outside criteria, and Excluded.
  - **Two @react-pdf traps:**
    - **Don't put `lineHeight` on the `Page` style.** Together with the page-number footer, it crashes any sector that runs past a few pages ("unsupported number: -7e+21"). Line height lives on the row styles, each with its own `fontSize`. A unitless `lineHeight` on a View without a font size resolves against the wrong size and roughly doubles the spacing.
    - **The embedded Tinos subset has no ✓ or ⚠ glyphs.** They print as blank space, so the PDF marks details with √ and ?. The Excel file and the web page use system fonts and keep ✓/⚠.
  - **Size and time:** measured on the 150 Poland companies, the PDF is 1.2 MB (192 pages) and renders in ~30s locally; the Excel file is 0.2 MB. Both are returned straight from the function, so they must stay under Vercel's 4.5 MB response limit. A 300-company report is estimated at ~2.5 MB. If reports ever get close to the limit, upload the file to Storage and redirect to a signed URL instead.
- **The system prompt** is the TRC Country Intelligence prompt, built in as `DEFAULT_SYSTEM_PROMPT`. Admins can override it in the `ci_system_prompt` singleton, and the previous text is saved to `ci_system_prompt_versions` on every save. A built-in project brief is appended after the prompt on every call: today's date, country, theme, sectors, revenue threshold, HQ rule, "ignore HubSpot", contact and source rules, and "search is mandatory". These per-project rules override the general prompt.

### Interview Tool research engine (migration 040, 19 Oct 2026, client request)
Admins pick who does the **web research** behind each interview's Background Research at `/admin/research-engine` (reached from the Interview Tool's gold "Admin tools" strip; admin-only via the `/admin/*` rule). **Claude writes the research and the interview questions either way**; only the searching changes. Stored in the `research_settings` singleton (`research_provider`, default `claude`); each run records the engine it used on `research_sessions.research_provider`, shown to admins in the interview's sidebar ("Web research"). The engine is read live at Generate time, so a change applies to the next run or regeneration, never to research already generated.
- **`claude` (default):** unchanged: one Claude call with the `web_search` tool (max 7 searches) under `SEARCH_POLICY` + the General Prompt.
- **`gemini`** ([research-engine.ts](src/lib/research-engine.ts), Gemini 3.8 Flash via `callGemini`, override with `RESEARCH_GEMINI_MODEL`) runs in two steps, then Claude writes:
  1. **PLAN** (no search): the category prompt becomes 4–5 search lanes of concrete questions about this interviewee, one lane per group of themes. The category prompt (25–30k chars) never goes to a grounded call, because the Interview Letter tests showed Gemini stops searching when a grounded prompt is that long. `ensureMandatoryQuestions()` guarantees the current-role/appointment-date check, the country's latest GDP/FDI/trade figures and the sanctions/controversy check. If the plan fails, the fixed `defaultLanes()` are searched instead.
  2. **SEARCH** (grounded, all lanes in parallel, up to 3 attempts each): short question-only prompts returning `F1 | fact | date | publisher` lines, each linked to its Google results via `groundingLinks(..., { keepUnresolved: false })`. Unresolved redirect links are dropped because they expire, and this research is read for weeks. A reply with no `webSearchQueries` is never used.
  3. **WRITE-UP** (Claude, no tools): system = General Prompt + `geminiWriteUpRules()` **last** (so it overrides the General Prompt's own "search / verify / check LinkedIn" steps); user = category prompt + documents + subject details + `renderWebResearch()`. `enforceSourcedUrls()` then removes any link that isn't one of the facts' pages (or in the attached documents / the user's notes), marked "(unverified link removed)"; it restores an unambiguous truncated copy and strips stray `[F3]` tags. The client gets the cleaned text as a final `{ final }` SSE event. The parser in `ResearchOutput` now buffers partial lines, because that one event spans network chunks.
- **Measured 19 Oct 2026** (Company Executive, Government Minister): the Gemini phase took ~24s and ~$0.024, ran 18–25 Google searches and returned ~50 facts across 4–5 lanes covering all 10 themes, every fact linked. It reported, with a source, that one test subject had left the role. The Claude write-up could not be measured locally (the local `ANTHROPIC_API_KEY` was rejected); its input is estimated at ~25k tokens, against 65–160k for the Claude engine, because there are no search results in context. - **Fallbacks, so research is never blocked:** no `GEMINI_API_KEY` → Claude. ### Copywriting: section structure & quotes (migration 041, 20 Oct 2026, client request)
The Configure form's free-text "Section structure", "Target length (words)" and "Quotes required" were replaced by a required, drag-and-drop **section structure** with a length in **characters** per section, plus **Direct quotes** and **Pull quotes** counts.
- **Section library = a label plus an optional description telling the AI what the label means** (`copywriting_sections.name`/`description`, admin at `/copywriting/admin/sections`, [SectionLibraryManager](src/components/copywriting/SectionLibraryManager.tsx)). E.g. "TEXT" → "the article's main body". It's sent after the section as "What this section is: …" in the ARTICLE REQUEST and the structure instruction, which tells the model to write exactly that kind of text in that section (so a section defined as the headline holds the headline, and only an undefined headline goes before the first marker). Writers see it too: hover a library section, or read it under the name on each row. It's snapshotted with the name. The same section ("Introduction") needs different lengths in different articles, so the length is set per article (in **characters** by default, or **words**: a per-row Chars/Words switch; snapshot `{unit, target}`, read through `sectionTarget()`, which treats an early snapshot's `target_chars` as characters; words are counted from the same plain text by `plainWordCount()`, with a ±2-word floor on the ±10% tolerance), on the row where the section was dropped ([SectionStructureBuilder](src/components/copywriting/SectionStructureBuilder.tsx): native HTML5 drag from the library and between rows, plus + / arrow buttons / arrow keys on the handle for touch and keyboard). The create route takes names from the library, never from the request, and stores a **snapshot** in `copywriting_projects.sections` (`[{key, section_id, name, description, target_chars}]`), so renaming or deleting a library section never changes an article. **No length limit** (client decision, 20 Oct 2026: the writer decides each section's length); only a whole number above 0 per section and at most 20 sections. Draft and Revision are therefore **streamed** (`streamWriter()` in the run route), with `draftMaxTokens()` sizing the output budget from the configured total, up to the model's 64k maximum, and a soft-deadline **timer** (draft 235s, leaving room for its automatic check; revision 275s) that aborts before Vercel's 300s cap. A cut-short reply has no final usage, so its output tokens are recounted with `countTokens` (the Usage ledger rule). A draft that stops early (deadline or `max_tokens`) is still saved, and its check report leads with a failed "Draft completeness" item. A revision that stops early is NOT saved, because a revision returns the whole draft and a partial one would drop the article's ending: the current draft is kept, the spend is billed and the writer is told to revise a few sections at a time. Roughly what fits in one step: about 15–20k output tokens in the time allowed, so about 50–70k characters.
- **Definitions:** a *direct quote* is the exact words of a person or source, word for word from the uploaded sources, in quotation marks and attributed. A *pull quote* is a short, attention-grabbing excerpt copied word for word from the uploaded documents, shown as a highlight; it doesn't count toward a section's length.
- **Markers, owned by code:** `structureInstruction()` (Draft, Revision) and `planStructureInstruction()` (Plan, Replan) are appended after the admin prompt, so they win over it. The model starts each section with a `[SECTION n: Name]` line and writes each pull quote as a `[PULL QUOTE: …]` line. `splitArticleImages()` turns both into segments: section markers are never printed (the draft views show a per-section length meter instead, via `ArticleWithImages`' `sectionTargets`), and pull quotes render as a gold-ruled highlight on screen, in Word and in PDF. Copy uses `articleForCopy()` (markers removed, pull quotes as blockquotes).
- **Lengths and quote counts are measured in code, never by the model** (it can't count characters). `structureCheckItems()` adds four items to every check report: Section structure, Section lengths (±10% is on target, or ±25 characters for a short section; ±20% is a warning), Direct quotes and Pull quotes. Each quote is also verified **word for word against the uploaded sources**, ignoring case, punctuation and spacing. Direct quotes are found by quotation marks (4+ words, so scare quotes don't count), so a count mismatch there is only a warning; pull quotes are exact marker lines, so a mismatch fails. `CHECK_STRUCTURE_CONTRACT` tells the model not to report on any of these.
- **Writer's brief vs TRC references, ranked in code** (`referenceUsageInstruction()`, appended after the structure instruction on Plan/Replan and Draft/Revision, so an admin prompt edit can't lose it). The writer's section structure decides **what** the article contains (sections, order, lengths, quote counts) and always wins. The TRC guides and worked examples decide **how** each section is written (opening hook, paragraph rhythm, how quotes are introduced, transitions, tone, closing). When an example is organised differently, the writer's structure is kept and the example's way of writing is applied inside it. With **no** section structure, the examples also set the article's shape. Facts only ever come from the sources and approved research. The plan notes which TRC technique each section uses, and the draft follows it. It's left out when the article type has no TRC guides or examples.
- **Check report is shown as the admin's Check prompt writes it (20 Oct 2026).** There used to be a contract forcing one `LABEL :: PASS|FAIL|WARNING :: detail` line per item, with a 2,000-token cap. A prompt asking for its own sections and tables then produced "gibberish": the parser's fallback copied the first 500 characters of the report into each of 6 default labels. Now:
  - `runCheck()` (run route) streams the Check step: 8,000 tokens, soft deadline.
  - `parseCheckReply()` keeps the reply as `checks.report`, rendered as Markdown with tables. Line-format items are still parsed when the reply is essentially only such lines.
  - The code-measured items (`structureCheckItems()`) are shown above the report.
  - Besides the shared material, the Check call receives the approved analysis, the approved plan, the writer's refine-chat requests, and `structureMeasurementsForCheck()`: exact section lengths, and each quote found / not found word for word in the sources, under "MEASURED BY THE SYSTEM". The contract tells the model to use those numbers and never count characters itself, and that in this tool a pull quote is an excerpt from the source documents.
  - Draft no longer runs Check inside its own request; the client runs it right after (`draftThenCheck()`), as it already did after every revision.
- **Projects configured before 041** have `sections = []` and keep the old behaviour everywhere: the legacy request block, no structure instruction, no structure check items. The old columns stay for them.

### Caja: consistent conversions, verify guard, deleting projects (28 Oct 2026)
- **A ticket's rate and amount always agree** (`settlement_amount = local_amount ÷ exchange_rate_used`). They didn't. Lucca's Kazakhstan card-app screenshots show both currencies ("₸1,700 / $3.81"), and the AI correctly took the dollars actually charged.   - `reconcileConversion()` is applied server-side on logging and on every edit:
    - same currency → rate 1;
    - a rate and an amount that agree to the cent are kept;
    - when they disagree, the settlement amount wins and the rate is derived from it with `rateFromAmounts()` (9 significant digits, tested on 200k random round trips).
  - `seedConversion()` ([finance-ai.ts](src/lib/finance-ai.ts)) gives each read entry its own starting rate:
    - the receipt's two amounts when it shows both;
    - 1 for the settlement currency;
    - the project rate for the project's local currency;

  - The upload form shows where each rate came from, re-seeds the rate when the currency is corrected, and only re-converts when the amount, currency or rate is edited.
  - The edit form sends amount/currency/rate only when one of them changed, so editing a concept never moves the money on an older ticket.
  - `conversionFlags()` judges the effective rate (local ÷ settlement, from 0.50 up), not only the stored one.
- **Verify refuses a clearly wrong conversion** (`conversionBlocker()` in [finance-review.ts](src/lib/finance-review.ts)). It blocks a ticket in the settlement currency that isn't 1:1, and an effective rate that's inverted or 10× or more off today's market rate. This matters because a verified ticket is locked for good. With no market rate, nothing is blocked. On the 66 pending tickets of 28 Oct 2026 it blocked exactly Jamaica's 20 reversed tickets plus three third-currency ones, and no others. Every verify caller (project page single and bulk, review queue, caja page) now shows the reason. They used to ignore failures.

- `computeBalance()` rounds its totals to the cent, so float noise can't show a red "-0.00" estimated balance.
- **Deleting a project** (`DELETE /api/finance/projects/[id]` `{ confirmName }`, Finance only):

### Formatted document standard (Topic Outline, Transcript, Interview Request Letter)
The **Topic Outline** (the Research module's "Interview Questions" output, `research_sessions.questions_output` — distinct from its "Background Research" output, `initial_output`, which this standard deliberately does NOT touch), **Transcript**, and **Interview Request Letter** `.docx` exports are "fully formatted, ready to use" per a fixed spec, defined once in [docx-standard-format.ts](src/lib/docx-standard-format.ts): Calibri 11pt, 1.15 line spacing (`276` in the `docx` package's twentieths-of-a-point convention), 1.9cm left/right margins, 2.5cm top/bottom margins (`STANDARD_MARGIN_TWIPS`, converted from cm at build time — don't hand-edit the twip values without recomputing), and a centred, bold, three-line header (`buildStandardHeader()`): title ("Interview Outline" / "Interview Transcript" / "Interview Request") / "Name, Designation, Company or Ministry" / "For publication in *Media Name*" (media name italicised in addition to bold). Deliberately **not** applied to Business Cases, Editorial Briefs, or Meeting Prep — those keep `docx-template.ts`'s own symmetric-margin/10.5pt page geometry untouched.

- **Two independent render pipelines both had to change.** Interview Letters already used the `docx-template.ts`/Calibri system (just needed asymmetric margins and 11pt instead of 10.5pt — `interview-letter-docx.ts` now imports its geometry from `docx-standard-format.ts` instead of `docx-template.ts`'s `MARGIN`/`SZ.body`). Research and Transcript downloads go through a completely separate system — the 8-brand "publication skin" picker in [download-templates/docx.ts](src/lib/download-templates/docx.ts) (real outlet-mimicking header/footer JPEG bands: USA Today, Newsweek, Guardian, etc.) — which was **Times New Roman/10.5pt** with its own margins before this change; its `FONT`/`SZ.body`/`MARGIN_X`/`MARGIN_TOP`/`MARGIN_BOTTOM` constants now come from the same standard. The branded header/footer JPEG bands are unaffected (they're images positioned by `header`/`footer` distance, independent of body margins).
- **`buildTemplatedDocx()`'s new optional `header` param** (`download-templates/docx.ts`) renders the standardised header INSTEAD of the old `heading` (H1) + `meta` ("Label: value" lines) block when present. The research download route ([sessions/[sessionId]/download/route.ts](src/app/api/sessions/[sessionId]/download/route.ts)) passes it only for `type=questions` (Topic Outline) — `type=research` (Background Research) keeps the old heading+meta format unchanged. The transcript download route ([transcriptions/[id]/download/route.ts](src/app/api/transcriptions/[id]/download/route.ts)) always passes it, for every variant (raw/refined/translated).
- **PDF exports (`?format=pdf`) are untouched** — [download-templates/pdf.tsx](src/lib/download-templates/pdf.tsx) has its own entirely separate constants (`Tinos` font, point-based margins) and doesn't import anything from `docx.ts`. This formatting standard is DOCX-only for now.
- **Transcripts needed new schema to have a header at all** — they previously carried zero interviewee metadata. Migration `024_transcript_interviewee_metadata.sql` adds `full_name`/`title_position`/`company_org`/`publication` to `transcriptions`, required on the upload form ([TranscriptionUploader.tsx](src/components/transcriptions/TranscriptionUploader.tsx)) before transcription can start.
- **Italic markdown (`*text*`) is a new capability in the shared renderer.** [docx-render.ts](src/lib/docx-render.ts)'s `styledRuns()` previously only parsed `**bold**`; it now also parses `*italic*` and `***bold+italic***` (longest-pattern-first so `***x***` is never misparsed as separate bold/italic tokens). This renderer is shared by both Topic Outline and Transcript downloads (`markdownToParagraphs()`), so it's the one place italics needed to be taught — `docx-template.ts`'s separate `renderTokens()` (business cases/briefs/meeting-prep) already supported italics and wasn't touched.
- **The Topic Outline's content-level style rules (bolding, italics, sentence case, one-page length, blank line between questions) are a fixed, non-admin-editable contract**, `TOPIC_OUTLINE_FORMAT_CONTRACT` in [generate-questions/route.ts](src/app/api/generate-questions/route.ts), appended as the LAST system block after the admin's general/category prompt — same "placed last on purpose so it overrides the admin prompt" pattern as the Document module's `OUTPUT_CONTRACT`. It instructs Claude to: group questions under `### Theme Label` headings (already rendered bold via the doc's heading styles, no separate renderer work needed), bold exactly one theme word per question, italicise publication names/foreign phrases/artwork titles, use sentence case (capitalising only proper nouns/publication+book titles/days/months/holidays/acronyms), leave a blank line between questions, and target ~400-500 words total to fit one page. This is prompt-level guidance, not a hard backstop — there's no natural approval-gate step in the research/questions flow to hook a word-count check into (unlike the Interview Letter's `ONE_PAGE_WORD_LIMIT`).
- **The outline is final, client-ready material from its first line to its last (19 Oct 2026, client request: users were downloading and sending it as is).** Measured on the 609 saved outlines: 212 had text before the first question (the General Prompt's Action Note + Tip + "DELETE THIS ACTION NOTE…", `PROCEED TO QUESTIONS`, self-check lists, replies to the editor's feedback, LinkedIn verification notes). 494 had internal notes after it or between questions, mostly `LEGAL / SANCTIONS / REGULATORY / REPUTATIONAL FLAG: …` and `EDITORIAL RISK FLAG`, which would have gone to the interviewee.
  - **Prompt.** `TOPIC_OUTLINE_FORMAT_CONTRACT` ends with FINAL OUTPUT RULES that override the General Prompt and category prompt. The outline starts at the first theme heading and ends with the closing question(s), with no working and no reply to feedback (it's applied silently). The rules say why: in this tool there's no separate "screen" for notes.
  - **Backstop.** [cleanOutline()](src/lib/outline-cleanup.ts) runs on save (the client gets the cleaned text as a `{ final }` event) and at read time for older outlines: the page, the poll, the download, and the "previous questions" fed into a regeneration.
  - **What it can never remove.** A question (a numbered one, or one that mentions sanctions, a flag carrier or a manual review mid-sentence), a theme heading, a "Qn." label, or the closing "CHOICE TWO / Last thoughts and reflections… and beyond" line in English or Spanish.
  - **What it removes.** Notes labelled at the start and their bodies; drafting breakdowns (`S1:`/`S2:`, word counts, ticks) when finished questions exist; and anything before "Producing final output now". A draft repeated in full keeps only its final version.
  - **Verified against all 609 outlines.** No real interview question is removed, no strong internal marker is left anywhere, and every removed question-mark paragraph was a drafting note.
  - **The Action Note's guidance now lives in the app.** It sits as a gold "Before sending" note above the questions (keep one closing question, fit one A4 page, sustainability tip), outside Copy and Download.
  - **Still in every outline by design:** the General Prompt's `CHOICE ONE:` / `CHOICE TWO:` closing alternatives, left for the editor to pick.
- **"Leave one line of space between questions"** is realised as a wider `spacing.after` on Topic Outline paragraphs specifically — `markdownToParagraphs()` gained an optional `paragraphSpacingAfter` param (default `120` twips, unchanged for every other caller); the questions download passes `240`. Every other paragraph type in the shared renderer (headings, bullets, speaker lines, plain text) also now sets `spacing.line: 276` for the 1.15 standard, regardless of this override.
- **Transcript refined-Word downloads used to show a duplicate title/byline/"For publication in …" line (24 Sep 2026).** The transcript refining prompt (admin-managed, `transcript_prompt`) predates the standardised header above and itself asks Claude to open the refined text with a title/byline/"For publication in `<publication>`" block, built from the same form-field values `buildStandardHeader()` now renders — see the `FORM_METADATA_INSTRUCTION` comment in [refine/route.ts](src/app/api/transcriptions/[id]/refine/route.ts) ("it kept writing 'For publication in Newsweek'"). Two fixes, since one alone doesn't cover already-refined transcripts: (1) `NO_DOCUMENT_HEADER_INSTRUCTION`, appended last in the refine route's system blocks (same override-the-admin-prompt pattern as `CONFIRM_MARKUP_INSTRUCTION`), tells Claude to stop emitting that block on every future refine; (2) `stripLeadingPublicationHeader()` in [docx-standard-format.ts](src/lib/docx-standard-format.ts) is a defensive backstop in `buildTemplatedDocx()` — whenever `header` is supplied, it detects and drops a leading block up through an unmistakable `For publication in …` line (plus a following `---` rule) from the markdown body, so transcripts refined before this fix also render clean without a re-refine. Matched only on that phrase, never touched otherwise. PDF is unaffected (per the bullet above, it never gained the standardised header to begin with, so there's nothing to duplicate against).
- **The refining prompt's "Disclaimer" blockquote now renders in red, in both PDF and Word (24 Sep 2026).** The admin prompt has Claude open every refined transcript with a `> **Disclaimer:** …` blockquote (a standing editorial note, not something the app generates) explaining the transcript is preliminary and that yellow-highlighted terms need verification — it was rendering in default grey/black since neither renderer had a way to key off it. `docx-render.ts`'s `markdownToParagraphs()` gained blockquote support from scratch (grouping `>`-prefixed lines, left border + italic, one paragraph per quote line) via a new `blockquoteParagraphs()`; `download-templates/pdf.tsx`'s existing blockquote case was rewritten to walk `tok.tokens` through `inlineNodes()` instead of dumping `tok.text` as unparsed lines (a pre-existing gap — bold inside a blockquote never rendered in the PDF at all). Both renderers detect "starts with `Disclaimer:`" (`/^\*{0,3}disclaimer\s*:/i`, ignoring the markdown `**`) and switch the quote's text + left-border color to red (`C00000`/`#C00000`); any other blockquote content keeps the original grey. Detected purely by that opening phrase, not a fixed/admin-editable list, so it tracks the live prompt without a code change if its wording is ever edited — as long as it still opens with "Disclaimer:".
- **The identity line is comma-only everywhere, including filenames (8 Oct 2026).** `joinIdentityForFilename()` used to join the name/title/company fields with an Oxford "and" before the last item ("Mr. ABC, CEO and XYZ Ltd.") for download filenames specifically, deliberately DIFFERENT from `buildStandardHeader()`'s in-document identity line, which was always comma-only ("Mr. ABC, CEO, XYZ Ltd."). The client flagged the inconsistency ("remove 'and', must be a comma everywhere") and it's now a plain `.join(', ')`, matching the header.

## API routes: resolve the user with `getApiUser()`, not a bare `supabase.auth.getUser()`

**Incident (14 Sep 2026, Sales Coach submit):** the create request hung until Safari gave up ("Load failed"), the immediate retry got a clean 401 "Unauthorized", and a page reload worked — all within 47 minutes of a fresh login, with the very same session accepted by Supabase Storage seconds earlier (both failed attempts' audio uploads succeeded). No Supabase or Vercel incident was posted. Two auth-js facts explain the whole sequence: its call to Supabase Auth has **no timeout**, so a slow answer hangs the route until the browser drops the connection; and it returns **any** failure to reach Auth — timeout, dropped connection, 5xx — as `{ user: null, error }`, which a route checking only `!user` reports as "Unauthorized". The user was never signed out.

**Rule:** API routes call [`getApiUser()`](src/lib/auth/api-user.ts). It races the auth call against a 12s timeout and separates two outcomes: a genuine auth rejection → 401 `Unauthorized`; a transient failure (timeout, `AuthRetryableFetchError`, HTTP 0/429/5xx, or a thrown network error) → 503 `{ retryable: true }` with `Retry-After`, and a `console.error` line so Vercel logs show it. Every Sales Coach route uses it; the other modules still call `getUser()` directly and carry the same exposure — convert them the same way when touching them. Clients that submit something valuable should treat 503/502/504/429/`retryable` and transport errors as "retry once after ~1.5s" (see `postWithRetry` in [SalesCoachForm.tsx](src/components/sales-coach/SalesCoachForm.tsx)), and the create route must make that retry safe — `POST /api/sales-coach` returns the existing row when the same audio path (or the same pasted transcript from the same user within 10 minutes) already exists, so a retry after a request that did land can't create a twin.

## Long client-side upload flows must refresh the session before each phase

**Bug this fixes:** a large audio upload (Sales Coach, Transcriptions) transcodes client-side with ffmpeg.wasm first — minutes of CPU-heavy work — then uploads directly to Supabase Storage, then calls a create API route. All three steps need a valid access token, but the token is only ~1h and supabase-js's background auto-refresh timer can fire late when the tab is backgrounded (Safari throttles inactive-tab timers hard) or the main thread is busy with wasm work. Symptom: the upload fails with a raw network error (Safari: "Load failed"; Chrome: "Failed to fetch"), immediately retrying gets a clean 401 `Unauthorized` from the API route (the stale cookie was resent as-is), and only a full page reload — which re-hydrates the session from the stored refresh token — fixes it.

**Fix:** `ensureFreshSession(supabase)` in [supabase/client.ts](src/lib/supabase/client.ts) checks the current session's `expires_at` and calls `refreshSession()` if it's within 2 minutes of expiring (or already expired), throwing a clear user-facing message only if the refresh token itself is dead (truly signed out elsewhere). Call it right before each step in a multi-minute flow that needs a valid session — after transcoding finishes, before the storage upload, and again before the final create call — both in [SalesCoachForm.tsx](src/components/sales-coach/SalesCoachForm.tsx) and [TranscriptionUploader.tsx](src/components/transcriptions/TranscriptionUploader.tsx). A new long-running client-side upload flow should do the same; a fast plain-file upload (research documents, receipts, document samples) with no transcoding step ahead of it is not at meaningful risk and doesn't need it.

## Key Decisions & Constraints

- **Modular workflows:** Research generation is a self-contained flow. Future AI workflows (e.g. question generation only, summarisation) should be added as separate modules without touching existing code.
- **Provider-agnostic AI layer:** The Claude client lives in `src/lib/claude/`. If the provider changes, only that layer changes.
- **Streaming output panes must use `useStickToBottom`** ([src/lib/use-stick-to-bottom.ts](src/lib/use-stick-to-bottom.ts)) — spread its `ref`/`onScroll`/`onWheel` onto the element that actually has `overflow-y-auto`. Never auto-scroll unconditionally (`scrollIntoView` on every token): it makes it impossible to read earlier text mid-stream. The hook needs BOTH signals — `onScroll` alone loses the race against a fast stream, because a programmatic pin can re-anchor the view in the gap between the user's gesture and the browser reporting the new `scrollTop`.
- **Token limit check happens before API call** — never after. A failed check must not incur any API cost.
- **Prompt versioning:** Every save to `general_prompt` or a category's `prompt_text` must snapshot the old version to the corresponding `_versions` table before writing.
- **Invite links are single-use and expire after 7 days.** The `handle_new_user` DB trigger marks the invitation `accepted` atomically on signup.
- **Admin cannot delete or change the role of their own account** — enforced in UI and should be enforced in API too.
